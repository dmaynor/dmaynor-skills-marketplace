# sat2 — Evolved Structured Analytic Techniques

sat2 keeps what earns its cost from classical SAT and drops what does not.
Empirically (sat-analysis 1.3.0 in production use), the hypothesis discipline
and falsification criteria paid; the ACH matrix, unanchored confidence
numbers, and reassure-first evidence ordering did not. This skill encodes
those findings as rules.

## Dual interface

sat2 is callable by a person, a model, or a tool.

**Human invocation** (default): `sat2 <subject> [mode]` — plain-argument
skill invocation; `mode` optional, auto-selected like sat-analysis if absent.

**Machine invocation**: the caller (another model, an orchestrator, or a
program) passes the entire argument as one JSON document:

```json
{
  "schema": "sat2.input.v1",
  "claim": "<the statement or question under analysis>",
  "mode": "STATEMENT_ANALYSIS",
  "observations": ["<camera-recordable facts only>"],
  "evidence": ["<documents, measurements, prior findings>"],
  "prior_findings": ["<results of earlier rounds, verbatim summaries>"],
  "output_format": "human|json|both",
  "budget_tokens": 4000
}
```

All fields except `claim` are optional. Unknown fields are ignored, not
errors.

**Response modes**:
- `human` (default) — the lean core in markdown (below).
- `json` — a single JSON document, schema `sat2.output.v1` (see
  `references/machine-interface.md` for the full contract and a worked
  example). No prose outside the JSON. A consuming tool must be able to
  branch on it without heuristic text extraction.
- `both` — one fenced JSON block labeled ```` ```sat2_output_v1 ```` followed
  by a prose summary of at most 150 words. This is the recommended mode when
  a tool invokes sat2 but a person reads the result.

**Error contract**: if the input is malformed JSON, or `claim` is missing,
respond `{"schema": "sat2.output.v1", "error": {"code": "bad_input",
"message": "<what was wrong>"}}` and stop. Never fabricate a partial analysis
over a bad input.

## Step 0 — Ceremony gate (run before anything else)

If a single mechanical test settles the claim — hash comparison, direct log
query, one API call, reading one function — run that test and report its
result. Do not run SAT on questions direct inspection answers faster.

Proceed past the gate only when at least one holds:

1. **Competition**: two or more plausible mechanisms genuinely explain the
   observation.
2. **Adversarial surface**: the claim is security-relevant or the analyst has
   a stake in the answer (daily-use tool, own code, own team's product).
3. **Downstream action**: someone else — a person, a model, a pipeline — will
   act on the conclusion.

In the response, state which condition fired. If none does, say so and stop:
that is the skill working as designed, not a failure to comply.

## Step 1 — Lean core (always emitted, prose, decision-relevant content first)

The lean core is the whole analysis for most invocations. Order it so the
first 40% of output contains the assessment and the discriminating test —
this is the truncation guard: what gets cut when the budget runs out is the
optional material, never the conclusion.

1. **O/I separation** (compact): observations a camera could record;
   anything requiring inference is restated as a hypothesis. No interpretive
   language in observations.
2. **Hypotheses**: minimum five, one line each, generated by at least two
   methods (actor enumeration, causal pathway, inversion, dimensional).
   Mandatory categories: an obvious/expected explanation, a null hypothesis
   ("nothing is wrong — thin wrapper, expected behavior"), and an
   uncomfortable hypothesis that challenges the analyst's assumptions and is
   distinct from the malicious/impostor hypotheses.
3. **Discrimination-first plan**: name the single cheapest test that would
   move the top-two hypotheses, first. Order the remaining plan by
   discriminating power per unit cost. Cheap reassuring tests (provenance
   checks that can only confirm the leading hypothesis) go LAST and must be
   labeled `provenance-only` with one sentence justifying their inclusion.
   Every planned action names which hypotheses it discriminates between.
4. **Falsification**: one sentence per hypothesis — the specific finding that
   would kill it. A hypothesis with no falsification criterion is not a
   hypothesis; it is a mood.
5. **Assessment**: conclusion, then confidence as term + numeric range +
   **basis**. The basis names its anchor: a measured rate, a historical
   frequency, a document, or an explicit `subjective prior` label. A number
   with no anchor is prohibited — "80%" presented as if measured when nothing
   was measured is exactly the failure mode this skill removes. If the
   assessment would change with the pending discriminating test, say which
   number moves with which result.

## Step 2 — Artifact budget gate

**ACH matrix: off by default.** The matrix restate priors unless it buys
something. Enable only when one holds:

- the caller explicitly asked for it,
- at least one additional round of evidence collection is already planned
  (so the matrix will be re-scored, not written once),
- the caller is a model or tool that will consume scored hypotheses
  programmatically (`output_format: json`).

When enabled, the matrix goes LAST in human output and is marked
`(optional artifact)`. Under truncation risk, emit the hypothesis×evidence
scores as compact JSON instead of a markdown table. Mode-specific catalogs
(breach, crash, fix, statement) from `references/` of the sat-analysis skill
remain applicable when relevant.

## Step 3 — Completion test (anti-substitution)

A full template is not a finished analysis. The analysis is complete only
when one holds:

- (a) the top-two hypotheses are discriminated by evidence already in hand,
- (b) the discriminating test is queued with a defined exit condition and an
  owner,
- (c) the caller declared the budget exhausted and the output names the one
  test that remains.

Every response ends with a completion statement naming which condition
holds. In `json` mode this is the `completion` object; in human mode it is a
final line: `Completion: <a|b|c> — <what was discriminated, or the queued
test and its exit condition>`.

The completion statement exists because the observed failure of classical
SAT is checklist substitution: five hypotheses, a confidence number, and a
phased plan can feel finished while the two tests that matter are pending.
sat2 makes that state explicit and reportable instead of cosmetic.

## Checklist (before emitting)

- [ ] Gate fired for a named reason, or test-and-exit happened.
- [ ] ≥5 hypotheses including null and uncomfortable; ≥2 generation methods.
- [ ] The discriminating test for the top two appears before any
      provenance-only action.
- [ ] Every prior states its basis or is labeled subjective.
- [ ] ACH matrix emitted only if gated in, last, and marked optional.
- [ ] Completion statement (a/b/c) present.
- [ ] In `json`/`both` mode: output validates against
      `sat2.output.v1` (run `scripts/validate_output.py` if available).

## Interaction with callers

- **From a model or tool**: honor `output_format` exactly; never append
  conversational filler to `json` output; include `prior_findings` in the
  O/I table so the caller can verify what was assumed vs. newly observed.
- **From a person**: the lean core is the answer; offer (do not perform)
  the escalation artifacts.
- **Iterative refinement** ("go deeper on H3", "more hypotheses", "challenge
  this"): re-emit only the changed section, re-checklist, restate the
  completion statement.
